# Airbnb Clone

A functional clone of the Airbnb marketplace built for the Scaler AI Labs SDE
Fullstack assignment - browse and search listings, view listing details, book
a stay for a date range, and manage listings as a host.

- **Frontend:** Next.js 14 (App Router, TypeScript, Tailwind CSS)
- **Backend:** FastAPI (Python)
- **Database:** SQLite via SQLAlchemy

## 1. Project structure

```

```

## 2. Running it locally

### Backend

```bash
cd backend
python -m venv venv && source venv/bin/activate   # Windows: venv\Scripts\activate
pip install -r requirements.txt
python -m app.seed        # creates airbnb.db and fills it with demo data
uvicorn app.main:app --reload --port 8000
```

The API is now at `http://127.0.0.1:8000`. Interactive docs (auto-generated by
FastAPI) are at `http://127.0.0.1:8000/docs` - useful for exploring every
endpoint during the evaluation call.

### Frontend

```bash
cd frontend
npm install
cp .env.local.example .env.local   # points NEXT_PUBLIC_API_URL at the backend
npm run dev
```

Visit `http://localhost:3000`.

## 3. Database schema

```
users             id, name, email, password, avatar_url, bio, is_superhost, created_at
listings          id, host_id -> users, title, description, property_type,
                   city, state, country, latitude, longitude,
                   price_per_night, cleaning_fee, service_fee_pct,
                   max_guests, bedrooms, beds, bathrooms, is_active, created_at
listing_photos    id, listing_id -> listings, url, position
amenities         id, name, icon
listing_amenities join table: listing_id <-> amenity_id  (many-to-many)
bookings          id, listing_id -> listings, guest_id -> users,
                   check_in, check_out, guests, nights,
                   nightly_rate, cleaning_fee, service_fee, total_price,
                   status (confirmed | cancelled | completed), created_at
reviews           id, listing_id -> listings, guest_id -> users,
                   booking_id -> bookings (nullable), rating, comment, created_at
wishlists         id, user_id -> users, listing_id -> listings, created_at
                   (unique on user_id + listing_id)
```

**Design decisions worth knowing for the interview:**

- **No separate "hosts" table.** Any user can list a property - whether
  someone is "hosting" is just a fact about whether they own rows in
  `listings`. This mirrors how Airbnb itself works and avoids a redundant
  role field that would need to stay in sync.
- **`amenities` is a real lookup table**, joined through `listing_amenities`,
  instead of a comma-separated string column on `listings`. That keeps
  amenity names consistent across listings and makes "filter by amenity" a
  plain join instead of string matching.
- **Bookings snapshot their own pricing** (`nightly_rate`, `cleaning_fee`,
  `service_fee`, `total_price`) instead of recalculating from the listing
  every time they're displayed. A host can change their nightly rate after
  a booking exists, and the booking should keep showing what the guest
  actually agreed to pay.
- **Booking overlap validation lives in application code**, not a DB
  constraint. SQLite doesn't have a clean way to enforce "no two rows with
  overlapping date ranges" as a table constraint, so `bookings.py` checks
  every existing confirmed booking for the listing before inserting a new
  one (see `dates_overlap` in `utils.py`). This is also why the booking
  endpoint returns `409 Conflict` instead of `400` on a clash - it's a
  concurrency-style conflict, not a malformed request.

## 4. API overview

All endpoints are served from the backend root; full interactive docs live
at `/docs`.

| Method | Path | Purpose |
|---|---|---|
| POST | `/auth/signup`, `/auth/login` | mocked auth, returns the user object |
| GET | `/listings` | search + filter (location, dates, guests, price, type, amenities) + pagination |
| GET | `/listings/{id}` | full listing detail |
| GET | `/listings/{id}/availability` | booked date ranges, used to disable dates client-side |
| POST/PUT/DELETE | `/listings` | host CRUD, ownership-checked via `host_id` |
| POST | `/bookings` | create a booking; validates guest count and date overlap |
| GET | `/bookings/user/{id}` | "My trips" |
| GET | `/bookings/listing/{id}` | host's bookings for one listing |
| POST | `/bookings/{id}/cancel` | cancel a booking |
| GET/POST | `/listings/{id}/reviews` | reviews for a listing |
| POST/DELETE | `/wishlist` | add/remove a listing from a user's wishlist |
| GET | `/users/{id}/listings` | host dashboard |
| GET | `/users/{id}/wishlist` | wishlist page |

## 5. What's mocked (per the assignment brief)

- **Authentication** - login/signup check a plaintext password column
  instead of hashing + issuing a signed session token. The frontend keeps
  the logged-in user in `localStorage` and sends their `id` with requests
  that need to know who's asking. Fine for a demo; a real build would swap
  this for hashed passwords and JWTs/sessions.
- **Payment / checkout** - clicking "Reserve" opens a checkout modal with a
  full price breakdown and a disabled, non-functional card form (see
  `CheckoutModal.tsx`). "Confirm and pay" creates the booking and shows a
  confirmation screen - the flow looks and feels real, but no payment
  processor is wired up, and the modal says so explicitly.
- **Messaging, identity verification, live map** - each has a real entry
  point in the UI (a "Message host" button, an "Identity verification"
  link, and a location section on the listing page) that opens a "Coming
  soon" modal explaining what's out of scope, instead of just being absent.
  The location section itself renders a static SVG map plotting the
  listing's stored lat/lng - not a real tile-based map (that needs a
  Google Maps/Mapbox API key), which the brief allows.
- **Photos** - seeded with `picsum.photos` placeholder images. Hosts create
  listings by pasting image URLs rather than uploading files.

## 6. Deploying

- **Frontend → Vercel:** import the `frontend/` folder as the project root,
  set `NEXT_PUBLIC_API_URL` to the deployed backend URL as an environment
  variable.
- **Backend → Render/Railway:** deploy `backend/` with the start command
  `uvicorn app.main:app --host 0.0.0.0 --port $PORT`, and run
  `python -m app.seed` once (a one-off job/shell command) after the first
  deploy to populate the database. SQLite is a single file on disk, so make
  sure the host's disk is persistent, otherwise the DB resets on every
  restart/redeploy - worth flagging as a known limitation of using SQLite
  in production, a Postgres swap would be the natural next step.

## 7. Assumptions made

- One currency (USD) across all listings, for simplicity.
- A guest can book their own listing (no check preventing hosts from
  booking their own place) - not addressed since the brief didn't call it
  out, but it's a one-line `if listing.host_id == guest_id` check to add.
- Reviews can optionally be tied to a specific booking; the UI only offers
  the "leave a review" button when it finds a `completed` booking for that
  listing under the logged-in user, but the API itself doesn't hard-require
  a booking reference.
- "Completed" bookings are set at seed time for demo purposes; there's no
  scheduled job that flips `confirmed` bookings to `completed` after
  checkout in this build.
